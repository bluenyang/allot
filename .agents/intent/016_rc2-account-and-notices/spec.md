## 요구 해석
- S-1 **계정에 남는 알림 기록** (intent 바라는 결과 1, 사용자 "둘 다 함 (추천)"): 종 알림의 읽음 표시와 저축 만기 카드의 "계속 보내기" 선택을 계정에 저장한다. 같은 계정의 어느 기기·브라우저에서 봐도 같다.
  - 만기 카드(spec 013 S-15): 저축 항목의 만기 달이 왔는데 월급 분배가 아직 그 통장으로 보내고 있으면 '대기 중인 변경'과 종에 뜨는 카드. '멈추기'는 그 항목의 멈춤 달을 데이터에 저장하고, '계속 보내기'는 데이터는 그대로 두고 그 카드를 더 띄우지 않는다는 선택이다(지금은 브라우저에만).
  - 지금의 뜻을 그대로 옮긴다: 읽음은 알림 id 단위(`src/lib/notices.ts`의 id), 만기 선택은 `계좌id@YYYY-MM`(`maturityKey`).
  - 목록에서 사라진 알림의 읽음은 지금처럼 버린다(`keptMarks`): 화면이 읽음을 저장할 때, 지금 목록에 없는 것은 함께 지운다.
  - 화면 상태라 변경 내역(`change_set`)에 남기지 않고 되돌리기 대상도 아니다(지금 localStorage도 그렇다).
- S-2 **처음 한 번 올리기** (사용자 "둘 다 함 (추천)"): rc.2를 처음 여는 브라우저는 localStorage의 `allot.notices.read`와 `allot.maturityKept`를 계정에 더한 뒤(합집합) 그 두 키를 지운다. 여러 기기에 있던 것은 합쳐진다. 실패하면 지우지 않고 다음에 다시 올린다.
- S-3 **행 수준 보안**: 새 표는 다른 사용자 데이터와 같은 규칙(`user_id`, `allot_owner` 정책, FORCE). 계정 옮기기(`OWNED`)에도 넣는다.
- S-4 **MCP** (intent 계획 3): MCP는 알림을 읽기만 하고 아무것도 누르지 않는다. `list_notifications`는 알림마다 `read`(true/false)를 주고, 계정에 "계속 보내기"로 남은 만기는 목록에서 뺀다(앱의 종과 같음). 도구 설명의 "브라우저에만 있어 볼 수 없다" 문장을 바로잡는다. 읽음을 쓰는 MCP 도구는 만들지 않는다(사용자 화면 상태).
- S-5 **비밀번호 추가** (intent 바라는 결과 2, 사용자 "최근 로그인 요구 (추천)", "흐리게 두고 안내 (추천)"): 비밀번호가 없는 계정은 설정 › 로그인·보안에 "비밀번호 추가" 칸이 보인다(새 비밀번호·다시 입력·만들기 버튼, 지금 비밀번호 바꾸기 칸과 같은 모양).
  - 서버는 Allot 경로 `POST /api/account/password`로 Better Auth의 서버 전용 `setPassword`를 부른다. 정책의 최소 길이는 `/set-password` 경로 규칙(`server/password-rules.ts`)대로 그대로 걸린다.
  - 관리자가 비밀번호 로그인을 꺼 두었으면 칸은 흐리게, "관리자가 비밀번호 로그인을 꺼 두었어요" 안내.
  - 로그인한 지 1일이 지난 세션이면(기준은 마지막 사용이 아니라 로그인한 시각, `session.createdAt`) "보안을 위해 다시 로그인한 뒤 만들 수 있어요" 안내와 로그아웃 버튼. 세션 자체는 7일(Better Auth 기본, 그대로).
  - 만든 뒤에는 목록에 '비밀번호'가 생기고 이메일+비밀번호로 로그인된다. 잠금 정책(spec 013 A-37)도 그대로 걸린다.
- S-6 **비밀번호 빼기** (사용자 "빼기도 함"): 이미 된다 — 로그인 방식 목록의 '비밀번호' 줄에 '해제'가 있고, Better Auth `unlink-account`가 마지막 한 방식은 거부한다(`FAILED_TO_UNLINK_LAST_ACCOUNT`, 화면도 버튼을 막음). 코드를 바꾸지 않고 시험(V-6·V-7)으로 확인한다. 뺀 뒤 그 비밀번호로는 로그인되지 않는다.
- S-7 **rc.1과의 관계**: 0.1.9-rc.1(intent 015)의 OAuth·`/mcp`·플러그인은 바꾸지 않는다. `list_notifications`의 결과 모양은 S-4만큼 넓어진다(필드 추가, 기계가 읽는 기존 필드는 그대로).
- S-8 **새 제한** (AGENTS.md "새 제한은 spec에 적고 승인"). 전부 새 기능에만 걸린다. 기존 입력(로그인, 비밀번호 바꾸기, 키, 도구)은 하나도 거부하지 않는다.
  - (새 제한 아님) 비밀번호 추가는 로그인한 지 1일 안의 세션만 받는다 — Better Auth `setPassword`의 기본 검사(`freshAge` 1일) 그대로, 사용자 "1일 (Better Auth 기본, 추천)". 넘으면 403과 안내.
  - 관리자가 비밀번호 로그인을 꺼 두었으면 **서버도 비밀번호 추가를 거부**한다(409, 안내). 화면만 흐리게 하면 API로는 만들 수 있게 되므로. (끈다 = 관리 › 로그인 방식에서 '비밀번호' 방식을 꺼서 모두 OIDC·GitHub·Google로만 로그인하게 하는 것. 관리자 누구에게도 외부 로그인이 없으면 서버가 끄지 못하게 막는다 — spec 006 S-11.)
  - 이미 비밀번호가 있으면 거부(Better Auth `PASSWORD_ALREADY_SET` → 409). 바꾸기는 지금의 '비밀번호 변경'으로.
  - 읽음·만기 기록: 기록 하나(알림 id나 `계좌id@YYYY-MM` 문자열)는 1~200자, 한 요청에 더하기·빼기 합쳐 500개까지, 사용자당 종류별 2000개까지(넘으면 오래된 것부터 지움, 거부하지 않음). 화면에 나오는 알림 수를 줄이지 않는다 — 목록에서 사라진 알림의 읽음은 함께 지워지므로 보통 수십 개.

## 설계
### 데이터 (W-1)
- `server/db/schema.ts`에 `noticeMark`(`notice_mark`): `user_id`(owner), `kind`(`read` | `maturity_kept`, check), `key`(text), `created_at`. 기본 키 (user_id, kind, key). `userScoped` 정책.
- `pnpm db:generate`로 마이그레이션, FORCE RLS는 `--custom` 마이그레이션(0038처럼). `OWNED`에 더함. `pnpm check:migrations`.

### 서버 경로 (W-2)
- `server/notice-marks.ts`(또는 routes):
  - `GET /api/notices/marks` → `{ read: string[], maturityKept: string[] }`.
  - `POST /api/notices/marks` `{ read?: { add?: string[], drop?: string[] }, maturityKept?: { add?: string[] } }` → 같은 모양의 새 상태. 한 트랜잭션, `asUser`. 더하기는 `on conflict do nothing`, 종류별 2000개를 넘으면 `created_at` 오래된 것부터 지움.
  - zod(`server/validation.ts`): S-8의 길이·개수.
- 변경 내역 기록 없음(S-1). API 문서 줄(`server/docs.ts`).

### 화면 (W-3)
- `src/lib/notice-store.ts`: 로그인한 세션이 생기면(`loadState` 뒤) 서버 기록을 읽는다. 읽음 표시·전부 읽음은 서버에 `add`(그리고 목록에 없는 것은 `drop`)를 보내고, 답으로 받은 상태를 쓴다(store가 서버 답을 받는 규칙). 서버가 답하기 전에도 화면은 바로 읽음으로 보이게(낙관적), 실패하면 되돌리고 오류 안내.
- `src/lib/goals.ts`의 `keepMaturity`도 같은 길로(`maturityKept.add`).
- 처음 한 번 올리기(S-2): 서버 기록을 읽은 직후, localStorage 두 키가 있으면 `add`로 보내고 성공하면 지운다. 세션 바뀜(`sessionScope`)을 지킨다 — 다른 계정의 표시가 섞이지 않게, 올리기는 그 브라우저에서 처음 로그인한 계정에만(아래 우려).

### MCP (W-4)
- `server/mcp/tools.ts` `list_notifications`: 기록을 읽어 `buildNotices`의 만기 목록에서 `maturityKept`를 빼고, 각 알림에 `read`. 설명 문장 고침. 다른 도구는 그대로.
- `state`·`hashState`에는 넣지 않는다: 넣으면 알림을 읽기만 해도 대기 제안이 stale이 된다.

### 비밀번호 (W-5)
- `POST /api/account/password` `{ newPassword }`(`server/account-routes.ts` 또는 routes): 비밀번호 로그인을 쓸 수 없으면 409 `{ code: 'PASSWORD_OFF' }`; 그다음 `getAuth().api.setPassword({ body, headers })`(정책 최소 길이는 기존 훅). Better Auth가 1일 신선함을 보고 `SESSION_NOT_FRESH`를 내면 403 `{ code: 'REAUTH' }`로 바꿔 답한다. 이미 있으면 409.
- `src/pages/Account.vue`: `hasPassword()`가 거짓이면 "비밀번호 추가" 칸(만들기·복사 포함). 성공하면 목록을 다시 읽는다. 문구는 ko/en.
- 빼기는 기존 '해제'(S-6). '비밀번호' 줄의 확인 문구만 "이 비밀번호로는 더 로그인할 수 없어요"를 더할지는 화면을 보고(바꾸면 조정 기록).

### 문서 (W-6)
- README(알림·로그인·보안 절), CHANGELOG(`0.1.9-rc.2` 항목은 릴리스 때; 지금은 Unreleased 아래), API 문서.

### 시험 (W-7)
- 단위: 기록 더하기·빼기·2000개 자르기(순수 함수로 뽑아), 처음 올리기 판단.
- API `tests/api/notice-marks.mjs`(`disposable.sh`): 두 세션 같은 계정에서 같은 상태, 다른 사용자 격리, 제한(201자·501개 거부, 2001개 → 2000), 비밀번호 추가(외부 로그인만 남긴 계정을 만들어: 관리자가 만든 사용자에 DB로 가짜 `github` 계정 행을 넣고 그 세션으로 비밀번호 계정을 해제 → 비밀번호 추가 → 그 비밀번호로 로그인), 로그인한 지 1일 지난 세션(DB에서 `session.created_at`을 이틀 전으로) 403, 이미 있을 때 409, 빼기(해제) 뒤 로그인 401, 마지막 한 방식 해제 거부.
- E2E `tests/e2e/rc2.spec.ts`(:15174): 두 브라우저 컨텍스트에서 읽음 맞음, 처음 올리기(localStorage에 넣고 열기 → 다른 컨텍스트에서 읽음), 만기 "계속 보내기"가 다른 컨텍스트에서도 사라짐(데이터가 있을 때, 없으면 건너뜀을 기록), 로그인·보안의 비밀번호 추가 칸과 오류 안내, 휴대폰 폭.

## 우려
- **처음 올리기와 계정**: 한 브라우저를 두 계정이 번갈아 쓰면 localStorage의 읽음이 어느 계정 것인지 알 수 없다(지금도 계정을 가리지 않음). 그 브라우저에서 rc.2로 처음 로그인한 계정에 올린다. 알림 id에는 계정의 행 id가 들어 있어 다른 계정에서는 대개 맞는 알림이 없어 해가 작다.
- **읽음 쓰기가 늘어남**: 알림을 누를 때마다 요청 하나. 종을 열어 볼 때 한 번 읽는다. 많지 않다.
- **신선함 기준은 로그인한 시각**: 앱을 매일 써도 로그인한 지 1일이 지나면 다시 로그인해야 비밀번호를 만들 수 있다. 비밀번호는 한 번 만들면 끝이라 불편은 드물다.
