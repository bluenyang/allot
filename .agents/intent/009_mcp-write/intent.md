## 문제
`docs/ROADMAP.md` 0.1.4 줄: MCP 쓰기 — 쓰기 도구, 확인 전 미리보기, AI 변경 묶음 되돌리기.

사용자 말:
> AI가 내 회계를 관리해줄 수 있다는 느낌으로. (2026-11-11)
> OAUTH를 써야 하니까 API Key 방식으로 MCP 쓸수 있게 하고. 권한은 읽기·수정 (2026-11-11, `.loctx/ROADMAP.local.md`)
> 일반적인 커밋 단위라고 생각해라. (2026-11-11, 되돌리기)
> 회계재무에 개인 정보가 많다. 이러면 보안문제도 다뤄야 함. (2026-11-11)
> intent 써봐 (2026-11-17)

0.1.3으로 AI 클라이언트가 API 키로 데이터를 읽을 수 있다(`/api/mcp`, 읽기 도구 6개). 하지만 AI가 대화에서 정한 것("이 구독 해지해 줘", "다음 달부터 생활비 10만 원 올려")을 Allot에 반영하려면 사람이 화면에서 다시 입력해야 한다.

## 바라는 결과
PM 해석:
1. **쓰기 도구**: AI가 MCP로 사용자의 데이터를 바꾼다 — 구독(추가·수정·해지), 플랜 전환 예약, 분배(단계 금액·대상·나머지 나누기), 기준 설정(월급·기준일·환율), 계획 일정·확인 항목. 변경은 화면과 같은 API 규칙(검증, 겹침 검사, 잠금)을 거친다.
2. **확인 전 미리보기**: AI가 바로 바꾸지 않는다. 먼저 "무엇이 어떻게 바뀌는지"(행의 전후 + 이번 달·다음 달 분배와 이체 금액의 전후)를 보여 주고, 확인을 거친 뒤에만 적용한다. 확인 방식은 열린 질문 1.
3. **커밋 단위 되돌리기**: AI가 적용한 변경은 하나의 변경 묶음(change set, 0.1.1)으로 남고, 누가(어느 키가) 했는지 보인다. 변경 내역 화면에서 되돌릴 수 있다(0.1.1의 revert 그대로).
4. **권한**: 쓰기는 키의 범위 `mcp:write`가 있어야 한다(0.1.3에서 범위 값을 미리 나눠 둠). 지금 있는 읽기 키는 그대로 읽기만.

## 계획
1. intent 승인 → spec 009: 도구 목록과 입력, 미리보기(제안) 저장과 수명, 확인 흐름, 변경 묶음의 행위자 표시, 키 범위 화면, W-n과 V-n.
2. 구현 순서(안): 쓰기 로직을 라우트에서 함수로 빼기(화면과 AI가 같은 규칙) → 제안 저장(스키마)과 미리보기 계산 → 확인·적용 경로 → 쓰기 도구 → 키 범위(`mcp:write`) 만들기·표시 → 변경 내역에 행위자(키 이름) 표시 → E2E·API 검사.
3. 검사는 `scripts/check-run.sh`로 돌리고 `pnpm check:logs`를 통과한 로그만 증거로 쓴다(0.1.3 회고, AGENTS.md). 스키마를 바꾸면 PR 전에 `pnpm check:migrations`.
4. review → test → PR·첫 감사 → 머지(사용자 지시) → rc → 테스트 서버(:15174, 비밀값 파일로 DB 유지) → stable(사용자 지시) → 둘째 감사 → retro.

- 문서: CHANGELOG, README(MCP 쓰기), `docs/ROADMAP.md`.

## 제약
- 인터넷에 노출된다: 쓰기 키는 읽기 키보다 위험하다. 쓰기 범위는 사용자가 키를 만들 때 직접 고른다. 키로 키·로그인·관리자 기능은 여전히 바꿀 수 없다.
- 모든 쓰기는 RLS 아래, 그 사용자의 데이터만. 화면과 같은 검증·규칙을 거친다(우회하는 경로 없음).
- AI 변경도 0.1.1의 변경 묶음과 되돌리기를 그대로 쓴다. 되돌리기 규칙(충돌 시 409 등)은 바꾸지 않는다.
- `calc.ts`는 순수하게(미리보기 계산은 calc를 부르는 쪽에서).
- 공개 저장소: 도구 예시·테스트에 실제 데이터 금지.

## 열린 질문
1. **확인 방식** — AI가 낸 변경을 누가, 어디서 확인하나요?
   - (a) **대화 안에서**: AI가 "제안" 도구로 미리보기를 받아 사용자에게 보여 주고, 사용자가 대화에서 승인하면 AI가 "적용" 도구를 부릅니다. 빠르지만, 승인이 대화 속 AI의 판단에 달려 있습니다(클라이언트의 도구 승인 창은 있음).
   - (b) **Allot 화면에서**: AI는 제안만 만들 수 있고, 사용자가 Allot의 "대기 중인 변경"에서 확인을 눌러야 적용됩니다. 가장 안전하지만 한 번 더 화면을 열어야 합니다.
   - (c) **키마다 고르기**: 키를 만들 때 (a)/(b) 중 고릅니다. 기본은 (b).
2. **AI가 바꿀 수 있는 범위** — 위 "바라는 결과" 1의 목록(구독, 플랜 전환, 분배, 기준 설정, 일정·확인 항목)이면 되나요? 표시 설정(테마·일반)과 공휴일 세트는 뺄 생각입니다. 삭제(구독 삭제 등)도 허용할까요, 해지·종료까지만 할까요?
3. **AI가 되돌리기도 할 수 있나요?** — 되돌리기 도구를 둘지, 되돌리기는 사람만(화면에서) 할지.

## 질의서 기록
—

### 에이전트가 정한 것
- **쓰기 로직은 화면 API와 한 곳**: 라우트 안의 쓰기 코드를 함수로 빼서 화면과 MCP가 같은 함수를 부른다. 대안: MCP가 내부적으로 HTTP API를 호출. 이유: 같은 검증·잠금·변경 묶음 기록을 보장하고, 세션 없이 키로 HTTP API에 들어가는 길을 만들지 않는다(0.1.3 S-5: 키는 `/api/mcp`에서만).
- **도구 호출 하나 = 변경 묶음 하나**: 확인 한 번으로 적용되는 제안 전체가 한 묶음이다(커밋 단위). 되돌리기도 그 묶음 단위.
- **미리보기는 저장되는 제안**: 제안 id, 내용, 계산된 전후, 만든 키, 만료(예: 15분)를 저장하고, 적용 때 데이터가 그 사이 바뀌었으면 거절하고 다시 제안하게 한다(낡은 미리보기로 적용 금지). 대안: 미리보기 없이 적용 후 되돌리기만. 이유: 로드맵이 "확인 전 미리보기"를 정했고, 금융 데이터라 적용 전에 숫자를 보여 주는 쪽이 맞다.
- **행위자 표시**: 변경 묶음에 키 id를 남기고(이미 `actor_kind = api_key`가 있음), 변경 내역에 "AI · <키 이름>"으로 보인다.
- **키 범위는 만들 때 고르고 바꿀 수 없다**: 범위를 바꾸려면 새 키. 이유: 이미 나간 키의 권한이 조용히 커지는 일을 막는다.

## 하지 않을 것
- OAuth 기반 MCP 연결(0.1.10), 앱 안의 AI 기능·LLM 키.
- 키·로그인·관리자 설정을 MCP로 바꾸기.
- 단발 지출·할부(0.1.5), 계좌 관리(0.1.6), 거래 내역(0.1.7) — 그 버전에서 해당 쓰기 도구를 더한다.
- 되돌리기 규칙 자체의 변경.
